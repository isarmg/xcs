# ZXS 介绍视频分镜

时长：220秒（3分40秒）。目标规格：1920×1080，30fps。语言：中文。叙事：问题 → 需求 → 操作过程 → 成功边界 → 实际界面。

## 演示约定

“项目方案.txt”、V1/V2/B1、目录组合及P01→B01→C01均为合成教学示例，不是用户真实资料。三份业务副本只是本片示例，不是系统强制最低份数；三成员控制元数据另计。实际Web画面须来自当前构建及演示账户，不能把示意动画标成实机。

## 逐场分镜

### s01 · 000–016秒 · 文件还在，过程却丢了

- 动画语义：pain
- 画面与动作：文件名层叠出现：“项目方案.txt”“项目方案_最终.txt”“项目方案_最终2.txt”。旧稿被覆盖，副本问号并列出现。此场为问题示意，不伪装产品UI。
- 屏幕副题：从一次普通的项目修改说起
- 递进提示：旧稿被覆盖 → 版本名越来越长 → 副本对应关系不明
- 旁白：方案改了几轮，旧稿被覆盖；另存的文件越积越多，却分不清哪份才对。硬盘里看似有备份，也说不清它保护的是哪个版本。

### s02 · 016–032秒 · 先拆开三个问题

- 动画语义：cause
- 画面与动作：把混乱文件分解为三列问句。沿问题逐项聚焦，不先堆产品名词。
- 屏幕副题：版本、方案和副本，各自回答不同的问题
- 递进提示：以前写过什么？ → 不同方案如何并行？ → 内容保护在哪里？
- 旁白：我们需要回答三个问题：以前写过什么，不同方案怎样并行，以及内容到底保存在哪里。只靠文件名和手动复制，很难把这些关系一直维护清楚。

### s03 · 032–047秒 · ZXS 如何组织这些关系

- 动画语义：solution
- 画面与动作：三层关系图依次出现：稳定文件身份→历史节点→盘位副本。用同一个合成文件贯穿后续。
- 屏幕副题：文件身份 · 历史节点 · 指定盘位
- 递进提示：文件身份不靠名称猜测 → 历史记录内容与关系 → 副本遵循指定盘位
- 旁白：ZXS 用稳定身份识别文件，用历史节点记录演进，用指定盘位管理副本。下面以一份项目方案为例，逐步看一次修改如何留下清楚的来路。

### s04 · 047–065秒 · 第一步：把内容变更留下来

- 动画语义：versions
- 画面与动作：工作区卡片进度变化；封存后出现V2 FULL完整文件块，V1保持原位。不得画成差量链解码。
- 屏幕副题：工作区修改 → 完整版本 → 发布
- 递进提示：工作区尚未正式发布 → 内容版本采用 FULL → 完整内容带来空间成本
- 旁白：修改先进入工作区，封存并发布后，形成新的完整版本，旧版本保持不变。正文改变后保存完整内容，会增加空间占用，换来每个版本都能独立读取，无需串起差量。

### s05 · 065–083秒 · 第二步：从旧稿开一个新方案

- 动画语义：branch
- 画面与动作：V1旁新增“方案B：待写入”标签，以虚线指向V1；正文文件数量不变。虚线明确为冻结引用，而不是合并关系。
- 屏幕副题：创建分支，只冻结来源引用
- 递进提示：选择真实历史版本 → 冻结来源引用 → 尚无本分支自有正文
- 旁白：想从第一版试另一条路，可以创建文件分支。此时只登记分支和冻结的父版本引用，不复制全文；主分支以后再变化，也不会把新方案的起点悄悄换掉。

### s06 · 083–100秒 · 真正写入，才产生自己的版本

- 动画语义：branch
- 画面与动作：在方案B工作区修改，发布时新增B1 FULL独立块；主分支V2和另一文件不动。
- 屏幕副题：首次写入 → 独立 FULL
- 递进提示：初始读取冻结父版本 → 首次写入建立独立 FULL → 其他文件保持原样
- 旁白：切换到新分支时，看到的仍是冻结的父版本。等真正写入并成功发布，新分支才拥有独立的完整版本；同目录其他文件不会因此跟着改变。

### s07 · 100–119秒 · 第三步：目录保存一整套组合

- 动画语义：workflow
- 画面与动作：以目录快照D1、D2分别列出方案、图纸、说明的精确节点引用；切换恢复完整列表。命名目录分支始终同一个。
- 屏幕副题：方案文件 + 图纸 + 说明 = 目录快照
- 递进提示：记录成员及精确引用 → 切换恢复完整组合 → 普通修改追加不可变子树
- 旁白：一个项目往往包含多个文件，目录分支记录它们的组成、名称和精确引用。切换目录时，恢复的是那套完整组合；普通修改追加目录快照，不会自动多出一个命名分支。

### s08 · 119–140秒 · 第四步：明确决定合并结果

- 动画语义：workflow
- 画面与动作：依次高亮两个参与文件分支、采用的节点、保留的归属。结果复用正文；其余参与分支标只读别名。不要显示自动逐行合并。
- 屏幕副题：选参与分支 → 选结果节点 → 选归属
- 递进提示：选择参与分支和结果节点 → 明确可写归属分支 → 其他参与分支成为只读别名
- 旁白：两条文件分支准备收拢时，先选择参与分支，再明确采用哪个节点的正文和标签、归属哪个分支。系统复用选定正文，更新相关目录引用；其他参与分支成为只读别名，不会自动拼接文本。

### s09 · 140–161秒 · 第五步：保护完成，才确认成功

- 动画语义：backup
- 画面与动作：先逐级亮起P01、B01、C01；另起独立一行表示控制元数据M1/M2/M3。全部满足才亮成功。穿插B01离线→等待/失败，不绕路。
- 屏幕副题：示例三份：P01 → B01 → C01
- 递进提示：份数包含主盘；按固定链放置 → 元数据三成员 ≠ 文件固定三份 → 达成保护与原子发布才确认
- 旁白：这次示例选择三份，包含主盘一份，沿指定链放到两块备份盘。只有目标副本、三成员控制元数据和发布条件都满足，才确认成功；指定盘不可用时，明确报告问题，等待恢复或调整配置。

### s10 · 161–183秒 · 需要回看时，知道能恢复什么

- 动画语义：restore
- 画面与动作：选旧节点读取；旁列已清除和不可用状态。外部备份作为独立故障域提示出现，不画永不丢失或自动复活。
- 屏幕副题：历史还在，不等于正文永远可读
- 递进提示：读取精确历史版本 → 从旧稿继续：建分支再保存 → 清除、不可用与可读分别显示
- 旁白：回看历史时，系统按精确版本读取；从旧稿继续工作，则创建分支再保存。已清除正文和副本不可用会分别显示；单盘只能读取本盘有效版本，完整恢复仍取决于保留材料和外部备份。

### s11 · 183–204秒 · 在实际 Web 界面里串起来

- 动画语义：web
- 画面与动作：使用当前仓库实际构建的Web截图或录屏，依次突出文件、真实历史树/分支、保护设置。必须保留“演示数据”标注。不可用伪造UI冒充真实录屏，捕获未完成时由主任务修订此场。
- 屏幕副题：文件 → 历史 → 分支 → 保护设置
- 递进提示：浏览文件与历史节点 → 查看文件分支及保护设置 → 真实界面；数据为演示用途
- 旁白：现在回到实际 Web 界面：先找到文件，再查看历史节点、切换分支，检查保护设置，把刚才的过程串起来。画面来自真实开发池，使用演示数据；项目持续开发，平台适配逐步完善。

### s12 · 204–220秒（3分40秒） · 让每一次修改都有清楚的来路

- 动画语义：outro
- 画面与动作：回到最初三个问题，逐一给出答案，收束到项目标题。末屏保留“项目持续开发中；能力以对应环境验证为准”。
- 屏幕副题：留住版本 · 分清方案 · 看清保护
- 递进提示：版本有记录 → 方案有来源 → 保护有明确边界
- 旁白：从旧稿覆盖的问题出发，ZXS 把版本、分支、目录组合和副本分开管理，再通过明确的保存过程连起来。知道改了什么，也知道保存成功意味着什么。

## 事实核对与制作边界

- `docs/02-concepts-and-invariants.md`：完整版本、不覆盖历史、业务保护与控制元数据、内容状态。
- `docs/06-history-and-branches.md`、`docs/11-write-semantics.md`：冻结来源引用、首写FULL、目录快照、工作区与保存屏障。
- `docs/design/file-merge-tags-backup.md`：显式文件合并、正文与标签选择、只读别名、目录引用推进；目录分支合并暂不实现。
- `crates/zxs-core/src/business/file.rs`：分支冻结来源引用；`file_merges.rs`：精确输入检查、选中节点复用/元数据节点、只读别名。
- `docs/09-backup-topology.md`：固定逐级路由、份数含主盘、不可跳过离线指定盘、同机故障域限制。
- `web/README.md`、`README.md`：实际Web功能及持续开发状态；不声称所有平台已安装验收。

以上为当前仓库设计与实现核对，不等同于物理故障、跨平台安装、签名分发或全部SMB应用的验收证据。

## 字幕和音频

story-timed.json 的 caption 是各场完整旁白，NARRATION.md逐字一致。字幕可按中文句号拆成2–3段，与场内动画阶段同步；不得把整段长文挤成单行。旁白应自然解释，避免营销口吻。若使用语音合成，需按场生成并测量长度，仅调整自然停顿或轻微语速；不可截断句尾。
