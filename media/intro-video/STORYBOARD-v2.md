# XCS v2 样片：改错以后，再试一个方案

28秒，1920×1080，30fps。仅新样片方案，不替换旧片、不渲染视频。完整片待声音与节奏确认后再做，目标105秒，允许90–120秒。

## 根本变化

旧版是12张解释卡片，观众先记概念，最后才能拼出用途。新版从第一秒就看见一行正文被改错，同一文件连续操作。每三秒出现可看懂的操作和结果；回看、开方案、验证并存各有自己的小闭环。讲到什么，就让画面立刻证明什么。

不靠更快切卡片、飘动图标或配乐掩盖静止。主要动作是选中文字、改字、点历史、选旧版、输入分支名、切换正文、观察保存结果。直到最后两次切换已验证，才出现两个方案的结果对照。

## 示例与事实边界

- 全片同一个文件：宣传方案.txt。
- 改动前：投放渠道：公众号。
- 误改后主方案：投放渠道：短视频。
- 从改动前建立方案B，再修改为：投放渠道：公众号＋社群。
- 误改版本只是被保留，没有被删除、覆盖或宣称纠正。选择新方案继续工作。
- 前提：演示中的旧版、误改后版本均已成功保存，且内容仍可读；不暗示任何已清除内容都能找回。
- 本样片全程为“操作逻辑演示 · 非实机录屏”，小角标常驻且可读。无伪造地址栏，无“真实开发池”标签，无假实机。
- 正文编辑是概念演示。真实Web源码中修改入口为“写入当前分支”，通过文件上传写入，并非内嵌文本编辑器。后续实录应使用外部编辑器改演示文件，再在Web实际上传，或验证其他真实支持的流程；不得把概念编辑区域包装成已实现功能。
- 源码已能核对历史节点的“创建分支”、文件详情的“当前分支”和“写入当前分支”；这只是静态核对，不代表完成了运行验证或录屏。
- 本脚本的“查看旧版”是意图表达。正式实录须验证实际可用的历史正文读取路径，不能因为有历史节点就杜撰点击直接预览能力。

## 声音、字幕与画面

约100字口语稿，像坐在旁边边点边解释。不要逐字念清楚，不要句句播音腔，不要为凑满3秒拉长尾音。先整段自然说，再对齐动作；下列语音窗口和字幕时间是制作目标，不是已测音频时间。若自然口播略有偏差，在25–30秒内微调动作边界；不能硬截句或填长静帧。

正文用大字，保留文件名和当前分支状态。字幕一行，长句最多两行，和按钮不重叠。不让旁白、字幕、讲解卡三份文字同时竞争。每个动作需要有按下/选中/结果反馈，不靠箭头暗示已经操作。

### 00–03秒 · 误改发生

旁白 / 字幕（0.15–2.85秒）：这行改错了，刚才还是公众号。

- 0.0–0.5秒：正文停在“投放渠道：公众号”；文件名常驻。
- 0.5–1.2秒：选中“公众号”，键入“短视频”；高亮只覆盖变动词。
- 1.2–2.1秒：按下保存，状态由“修改中”变成“已保存”。
- 2.1–3.0秒：光标返回改动词，出现短提示“改错了”；不展开流程。

### 03–06秒 · 找改动前版本

旁白 / 字幕（3.15–5.85秒）：打开历史，点改动前这版。

- 3.0–3.8秒：指针点击“历史”；右侧抽屉展开，正文保持可见。
- 3.8–4.7秒：只出现“刚才：短视频”和“改动前：公众号”两条记录。
- 4.7–6.0秒：点击“改动前”；选中底色落下，正文预览即将切换。

### 06–09秒 · 旧内容能读到

旁白 / 字幕（6.15–8.85秒）：公众号，还在这儿。

- 6.0–6.5秒：正文明确替换为“投放渠道：公众号”，标题显示“查看旧版”。
- 6.5–7.5秒：短暂显出旧值/现值差异，只有“公众号”与“短视频”两词参与。
- 7.5–9.0秒：差异提示收起，指针移到当前旧版旁的“创建分支”；正文仍可读。

### 09–12秒 · 从旧版起步

旁白 / 字幕（9.15–11.85秒）：就从这版，另开一个方案。

- 9.0–9.8秒：点击选中旧版旁的“创建分支”；不点击当前最新版。
- 9.8–10.8秒：分支命名输入框出现；明确显示“起点：改动前”。
- 10.8–12.0秒：键入“方案B”；不播放复制正文或复制文件的动画。

### 12–15秒 · 进入新方案

旁白 / 字幕（12.15–14.85秒）：叫它方案B，切过去。

- 12.0–12.6秒：提交命名；分支选单新增“方案B”。
- 12.6–13.5秒：展开选单并选中“方案B”；标题状态切到方案B。
- 13.5–15.0秒：正文仍为“投放渠道：公众号”；小字“沿用所选旧版”出现后淡出。

### 15–18秒 · 只改新方案

旁白 / 字幕（15.15–17.85秒）：加上社群，再保存。

- 15.0–15.6秒：进入明确标注“内容编辑示意”的正文区域；光标定位句尾。
- 15.6–16.7秒：逐字输入“＋社群”；新增字符高亮，原“公众号”保留。
- 16.7–18.0秒：触发“保存到方案B”示意动作；状态变成“保存中”。

### 18–21秒 · 保存得到确认

旁白 / 字幕（18.35–20.85秒）：好了，方案B存下来了。

- 18.0–18.2秒：保存中状态消失，结果状态变为“方案B已保存”。
- 18.2–19.8秒：仅此时新增方案B自己的版本标记；不得在创建分支时提前出现。
- 19.8–21.0秒：指针打开分支选单，准备验证另一个方案。

### 21–24秒 · 验证主方案没被覆盖

旁白 / 字幕（21.15–23.85秒）：切回主方案，还是短视频。

- 21.0–21.7秒：点击“主方案”；选单关闭，分支标题先更新。
- 21.7–22.4秒：正文切回“投放渠道：短视频”。
- 22.4–24.0秒：刚才方案B的正文缩成右侧留样；主区域仅高亮“短视频”。

### 24–28秒 · 验证两方案并存

旁白 / 字幕（24.15–27.85秒）：方案B也在。两条路，都留着。

- 24.0–24.7秒：再打开分支选单，点击“方案B”。
- 24.7–25.4秒：正文回到“投放渠道：公众号＋社群”。
- 25.4–26.6秒：已验证的主方案留样置左，方案B正文置右；此时才出现双方案对照。
- 26.6–28.0秒：分别强调“短视频”和“公众号＋社群”；末尾停留不超过1.4秒，不加片尾口号。

## 三个可独立理解的小闭环

1. 0–9秒：正文改错 → 打开历史并选旧版 → 看见“公众号”仍可读。
2. 9–21秒：想换思路 → 从所选旧版建方案B、切过去、加社群、保存 → 方案B保存成功。
3. 21–28秒：担心覆盖另一方案 → 来回切换 → 两种正文都能读到。

创建分支时只新增名称和旧版起点关系，不复制整张正文卡、不冒出新内容版本。写入成功后才出现方案B自己的版本标记。最终双栏是已展示结果的编辑对照，不是假称Web自带并排比较功能。

## 后续完整片（先不制作）

- 0–28秒：本样片。
- 28–50秒：方案加配图，切换一次看见整套组合变化；只展示当下两份文件。
- 50–72秒：明确选定采用哪版，展示合并后的归属和只读结果；不演自动拼文本。
- 72–96秒：保存中和保存成功的可见差别；实际展示保护状态与不可用时的反馈，术语留给说明文档。
- 96–105秒：回看可读版本，同时交代“已清除/不可用”边界，结束在操作结果。

实际Web录屏与概念段必须逐段标识。真实录屏使用演示数据和当前构建，并记录来源和操作路径；有剪辑加速应标注。只有跑通动作并录到结果才能写“实机”。若实际操作需要更长时间，优先减少完整片的主题，不把关键步骤剪没。

## 样片验收门槛

- 静音观看：能指出哪里改错、从哪版开始、哪次保存、为何证明两方案都在。
- 只听声音：普通人能听懂，不需要先知道版本树、FULL或元数据。
- 每个3秒段都有正文/选择/保存状态的因果变化；单纯镜头移动不算通过。
- 字幕逐句用最终音频重新对齐；听完整段，不以音量检测或时间表代替试听。
- 28秒样片先确认声音和节奏，再扩完整片。源码可提交；视频、音频、录屏和合成中间件不进GitHub。

实现参考：web/src/files/detail.rs、web/src/files/version_tree.rs、web/src/files/branch.rs。新JSON是逐动作制作规范，不与旧render.py隐式兼容；不得未经改造直接套旧卡片渲染器。
