## 19.1 按完整文件及实际位置计费

对仍保留的不同完整版本，按各版本实际目标盘位核算，普通后续提交引用的同一未变版本不重复计费。分支实际写入生成的完整版本独立计费；合并连线只计少量关系元数据，拆分后两树不通过共享文件抵消占用。

这里的合并连线指旧 `MergeLink`。文件分支合并 `FileBranchMerge` 同样复用已有正文，但需计入来源记录、必要的元数据节点及受影响目录子树，不能只按一条关系线估算其元数据预算；规则见[补充说明](design/file-merge-tags-backup.md)。

```text
完整内容预算 ≈ Σ[logical_size(v) × target_copies(v)]
总需求 = 完整内容 + 历史拓扑与元数据 + 工作区
       + 分支首写/拆分/拓扑迁移的临时占用
       + 修复预留 + 安全余量
```

各物理盘上的副本分别计费。Btrfs 压缩、稀疏、分配和元数据会影响实际占用，逻辑大小、保守预算及实际物理占用分别报告。墓碑发布不等于所有盘已释放空间，暂存和迁移残留也不能隐藏在正常内容预算里。

<a id="s19-02"></a>

## 19.2 全量版本的成本例子

10 GiB 文件保留 100 个完整版本、每版三份，内容预算约为 3000 GiB，即 2.93 TiB，另加元数据、工作区和维护预留。即使某次只修改 4 KiB，新的完整版本仍需按 10 GiB 及目标份数预留。

为含 200 GiB 文件的状态创建分支只占用元数据和冻结来源引用，不预先复制 600 GiB 正文；只有随后实际写入该文件并要求三份保护时，新的 FULL 内容预算约为 600 GiB。两个分支间的合并连线仅占用关系元数据空间，不产生文件复制开销。上述为字节量估算，不是实际空间测量或耗时承诺。

<a id="s19-03"></a>

## 19.3 分支、拆分与迁移预留

活动继承分支仍固定所需父正文，引用虽然不新增 payload 字节，却可能延长父内容保留；不能预先将被依赖父版本计作已可释放。

分支创建只准入元数据与来源引用开销；首次实际写入时再为该文件完整逻辑大小及指定副本预留空间，不因登记引用提前占用全部来源正文预算。合并连线不复制文件，无需预留额外内容空间。拆分先准备新树的独立文件及两树恢复包，拓扑迁移先准备新指定目标；不能先删除原健康文件腾空间。

准备对象可在同盘封存为正式路径，避免同一新文件无意义再复制，但不能用 reflink、硬链接或跨树引用降低独立文件预算。所有计划展示峰值占用、最终预计占用、可取消阶段和实际释放条件。历史清除不需要重写后续完整版本，但仍需保留墓碑及清理任务的元数据预算。

<a id="s19-04"></a>

## 19.4 读写与前台应用成本

大小 S、目标 r 份的新版本，内容写入通常约 r×S，另计工作区构建、校验和元数据。按范围上传可以减少网络量，不能减少完整版本及其指定副本的最终预算。

小文件频繁保存、持续打开的大文件和写穿透请求要分别测试。用户可选择是否启用周期检查点及其频率，界面展示空间成本；系统不通过改用其他保存方式隐藏全量保存代价。

<a id="s19-05"></a>

## 19.5 优化顺序

先验证完整字节、正确路由、原子发布和独立恢复，再优化范围缓存、预读、并行副本复制和后台调度。优化不能提前报告保护完成，不能省略首次写入 FULL 版本所需的完整文件封存，也不能让拆分结果继续引用另一树文件。

巡检、修复、分支首次写入及拆分任务应有进度、并发和带宽限制，可在安全阶段暂停或取消，避免后台任务持续阻塞日常 SMB 和 Web 文件操作。已进入不可撤销决定的任务继续按原操作恢复。

<a id="s19-06"></a>

## 19.6 应用看到的剩余空间

SMB 共享的容量信息只能返回保守可写预算，还受目录一级规则、份数、固定目标、配额和预留影响；不能把 n 块盘剩余容量简单相加作为共享可写空间。

共享内不同目录的路由可能不同，单个总数无法保证每个文件可写。最终保存仍执行逐文件、逐指定目标的准入检查，错误定位到对应盘位、来源和级别。

<a id="s19-07"></a>

## 19.7 容量预警与写入准入

每仓库、历史树、一级来源和备份目标分别显示当前内容、保留历史、独立分支、合并连线元数据、已清除节点、实际文件占用和计划预留。汇聚备份盘列出各来源贡献；实际残留副本单列，不计正常保护但仍计物理占用。

默认业务预算达到 80% 预警、90% 严重预警，根据最近 7 天增长估计剩余不足 30 天时提示增长风险。样本不足显示未知。这些是可配置的初始值，预测不替代实际准入。

每盘默认至少预留 10% 安全余量，并独立计算下一份检查点、未决事务及一次成员恢复所需的元数据预算，取较大要求。内容修复另有预算，不能挪用恢复控制记录所需空间。检查 Btrfs 实际可分配数据和元数据空间，不仅依赖表面空闲数字。

保存前在每个冻结目标登记空间预留，防止并行工作区共同超卖。候选阶段预留保留到结果收敛；未知长度上传逐步申请，额度不足停止接收并保留已接收数据。预估与预分配不能替代实际写入、校验和同步结果。

达到硬配额或恢复余量不足时，拒绝新增增长并暂停可取消后台任务；读取、导出和预算内必要恢复继续开放。扩容须经设备登记及来源映射检查，普通启动不自动格式化新设备。

<a id="s19-08"></a>

## 19.8 发布前的性能基准

记录硬盘与总线、网络、服务器、Samba 和客户端版本、文件大小及数量、r(v)、缓存状态、校验段大小和保存频率。分别测顺序和随机读取、首次打开、目录分页、小文件批量保存、大文件局部修改后的完整保存、分支创建与首次写入、合并连线保存、独立树拆分、历史清除、拓扑迁移与故障修复。

报告 P50/P95/P99 延迟、吞吐、实际读写与网络字节、CPU、内存、缓存命中和后台任务影响。比较不同校验段大小时保持完整性验证；跨平台结果分别记录。不能由字节放大比例推导同倍延迟，也不把架构估算写成已测性能。

<a id="s19-09"></a>

## 19.9 可用性与性能目标登记

每个候选发行版在测试前登记下表的数值、数据规模及负载条件。数值属于该环境的验收目标，不能先跑出结果再把目标改成通过；目标未填写、证据缺失或超过目标都不能通过相应验收。模板见[验证报告模板](templates/validation-report-template.md)。

| 指标 | 必须固定的测量边界 |
| --- | --- |
| 保存 P95/P99 | 从显式提交或 SMB 屏障开始，到最终保护并公开；分文件大小、修改比例、份数和同步频率 |
| 排队与决定槽位时长 | 分开测准备队列、ACCEPT 至 PUBLICATION/索引应用，不隐藏全池阻塞 |
| 故障恢复时间 | 分别测故障发现、恢复材料及替换盘就绪后的收敛时间、总停止写入时间；不能把等待换盘从总停写时间隐藏 |
| 索引重建与单盘导出 | 固定历史节点数、文件数、元数据量及并发 I/O，验证内容后才算完成 |
| 后台干扰 | 巡检、分支首次写入或拆分开启后前台 P99 和吞吐变化 |
| 已确认数据恢复点 | 在声明故障模型、健康副本及控制证据条件下，不丢失已确认决定；单份内容所在盘永久损坏仍可能丢失内容，不承诺无条件 RPO=0 |

初始运行告警建议：决定槽位未收敛 30 秒发警告、120 秒发严重告警，排队 30 秒发警告。这些是可调的诊断阈值，既不是性能承诺，也不授权超时回滚。超过阈值定位具体盘和阶段，停止扩大队列，优先恢复控制证据；需要关闭入口时明确报告受影响范围。

## 19.10 工作资源上限与长期增长

以下为首轮样机的初始准入值，实际发行需按负载测试调整；字节限额与第 19.7 节逐盘预算同时生效，取更严格者。超过限额拒绝新增工作，保留已有脏数据和未决证据。

| 资源 | 初始上限或策略 |
| --- | --- |
| 每账户未结束工作区 | 32 个，包括断连及失败待处理工作区 |
| 每账户 / 全池并发上传 | 4 / 16 个 |
| 每账户 / 全池暂存字节 | 100 GiB / 500 GiB，含旧脏代际和失败上传，不重复计算同一物理工作文件 |
| 每会话 / 全池开放句柄 | 256 / 4096 个 |
| 全池待准备或待提交任务 | 128 个；账户公平排队；已 ACCEPT 的决定不因队列上限丢弃 |
| 每页目录条目 / 每次事件返回 | 默认 200，最大 1000；客户端不能申请无限列表 |
| 分页快照有效期 | 15 分钟；授权变更或树迁移可提前使游标失效 |
| 在线事件重放窗口 | 最长 7 天，并设 1 GiB 总预算；到任一边界即可裁剪通知，返回游标过期；不裁剪权威业务证据 |
| 未处理工作区提醒 | 7 天无活动后提醒，之后每 7 天提醒；时间到期不自动删除内容 |

恢复日志、操作查询、取消、导出和必要维护使用单独额度，不与新上传抢占全部资源。服务启动及故障恢复先重建工作区账本和预留，之后才接纳新增任务；离线内容保留占用不能因断连从账本消失。

管理员可暂停失联账户的新上传，通知所有者保存、导出或明确放弃。放弃必须有授权、作用范围、操作记录及未决检查；未知提交先收敛，不能用放弃绕过决定。读取租约设置有限期限并按当前权限续约；PURGE_PENDING 后不接纳新租约或续约，既有租约在已授予期限内结束，避免无限续租阻塞清除。

历史目录、墓碑和操作去重摘要按长期增长核算：分别测每个提交、版本、操作和连线的平均元数据字节，报告总量、增长率、检查点峰值内存/空间及重建时间。接近元数据预算时拒绝新增长并告警，不能以日志裁剪为由删除仍需的历史或去重事实。长期归档和整池销毁另有显式流程。

## 19.11 文件历史候选索引与资源限制

`Engine::file_history` 保留原有完整数组和排序语义。SQLite 的 `file_history_versions` 仅提供候选版本 ID，使用 `(file_id, version_sequence_key, version_id)` 索引；序号采用 8 字节大端编码，覆盖完整 u64 范围，同序号按二进制 ID 顺序返回。返回对象始终从权威内存 State 读取，授权仍由原有业务层执行，不读取 JSON 投影来授予权限。

候选集合的完整性由恢复后 State 生成的每文件计数校验；后续复用已有版本变更 delta 更新计数和类型化索引，不增加第二遍全版本扫描。类型化行、通用实体行和投影序号在同一事务中提交。每个变更版本会额外写一行类型化索引，不能把原通用实体写入计数当成全部 SQLite 写入成本。可信计数另占 O(文件身份数) 内存，不保存第二份完整 State。

读路径在同一 SQLite 快照中先核验三个查询对象的精确类型和 DDL，再检查投影序号、候选数、顺序及每行字段。缺行、伪造归属、损坏、数据库缺失、异常 schema 或锁竞争均回退到完整 State 扫描；失败后停用候选路径，只有从权威 State 完整重建后才恢复，普通增量写入不解除停用状态。读取连接不创建文件且只读，保持 WAL/FULL 和防御模式，忙等预算为 20 ms；连接限制单值/编码行 64 KiB、SQL 16 KiB、编译 VM 程序 10,000 操作及 16 个绑定参数。编译 VM 限额不是运行时间超时；因此必须在读取内容前拒绝替代视图。

连接与逐行校验成本会使小规模查询更慢，因此当前采用保守路径选择：总版本至少 300,000 且目标文件版本不超过 100 时才尝试 SQLite，否则直接使用原扫描。这只是内部执行策略，**不是分页、响应条数或历史保留上限**。生产候选查询最多分配 101 行（含一行超额检测）；不同环境须测量索引连接、逐行校验和扫描成本，不由 EXPLAIN 查询计划推导延迟收益。可用 `cargo test -p storage-engine --release measure_history_candidate_latency --lib -- --ignored --nocapture` 重跑合成测量。


### HTTP spool 的资源边界

当前服务已为 `api-spool` 实现每账户/HTTP 全局累计预留和启动盘点，计入旧代际、失败上传、完成但仍保留的副本及未知文件，并为每个数据文件计入保守元数据开销。默认额度分别为 100 GiB 和 500 GiB，所在文件系统另保留 1 GiB 恢复余量；同代重试不复制正文。具体配置和取消/同步失败语义见[服务端组件](components/server.md#http-spool-budget)。

这不是上文设计目标中跨 HTTP、引擎工作区和 SMB 的统一暂存账本。核心的 `max_workspace_bytes` 仍单独限制其目录；其他协议的句柄、公平性与全池预算见各组件的当前限制。文件长度计费不等于实际分配块数，空闲余量也不能阻止外部进程占用空间。达到上限时拒绝新数据，不通过丢弃历史、回执或未决字节来腾出额度。

### 持久工作区证据准入

`max_workspaces` 继续限制 open/sealed 工作区。另设跨状态、跨重启的证据预算：
`max_retained_workspaces` 默认 4096 条，
`max_retained_workspaces_per_principal` 默认每主体 1024 条；
`max_retained_workspace_metadata_bytes` 默认 128 MiB，
`max_retained_workspace_metadata_bytes_per_principal` 默认每主体 64 MiB。
旧配置缺少这四项时使用上述默认值；字节配置仍使用十进制字符串。

字节计费为每个工作区规范 JSON 清单的逻辑长度，按 committed 状态与最大 fence
及暂存文件的提交后上下文（固定宽度 ID / 最大代际）预留关闭/恢复空间；镜像副本不重复计费。这不是新增缓存，也不是文件系统实际块数预算。
上传完整代际仍受每工作区 `max_workspace_bytes` 限制，保留记录数为其总量提供有限上界。
创建、清单增长和启动加载均执行预算检查；aborted、committed、过期工作区仍计费，
不会通过反复创建/中止释放额度。失败的写入若可能留下持久证据，停止新写入并要求重启核对。

达到预算时拒绝新增或增长，不自动删除未决字节、提交回执或其他恢复证据。
因此这是保守的准入上限，不是自动回收策略。当前没有安全退休工作区证据的实现：
4096 / 1024 是池 / 主体的累计生命周期记录上限，而非同时活动数；正常成功提交也会消耗名额。
按每个主体每天 100 次新建并提交计算，默认主体记录名额约十天耗尽，不能当作无限期生产容量。
部署前须依据保存频率、主体数量及预计服务周期规划配置；当前版本没有既有池配额变更或证据退休命令。

管理员可在 Web“系统状态”的“持久工作区证据配额”查看全池和当前账户的记录数、
预留元数据用量及上限。`GET /api/workspaces/capacity` 返回实时只读诊断：普通已认证账户
只得到自身用量，管理员另得到全池汇总；不返回其他账户标识或逐账户用量。
`records` 与 `metadata_bytes` 的 `used`、`limit`、`remaining` 均为十进制字符串，
其中字节含生命周期预留，不代表磁盘空间。任一可见维度使用至少 80% 返回 `near_limit`，
达到上限返回 `exhausted`；`ok` 仅说明这些维度尚有余量，不保证下一次请求一定能接纳。
请求可能同时受活动工作区、文件长度、磁盘余量和单清单格式上限限制。
准入错误保留 `RESOURCE_LIMIT`，并指出全池/主体的记录数或元数据字节维度。
该诊断用于提前暴露累计上限，**不解决生命周期耗尽，也不授权删除恢复证据**。
安全退休仍须独立证明操作所有者、请求摘要、结果与重试语义、活动读租约、fence 和恢复证据均被保留；
不能仅删除终态清单或只增大配额就宣称问题已解决。

64 MiB 的主体逻辑字节默认值与既有单清单读写上限一致；128 MiB 全局预算最多容纳两份
满额逻辑清单。这些是准入阈值，不是预分配缓存或实际内存占用保证。计费还包含保守的
关闭/提交上下文预留，因此并非任意原始长度小于 64 MiB 的工作区都能被接纳。
若实际清单或其生命周期预留超过单清单 64 MiB 上限，必须在持久化或发布前拒绝，
不会把预留截断到 64 MiB 来掩盖提交后的回执超限；提高总配额也不能绕过单清单格式限制。

受支持的配置入口是未初始化草稿：由 `zxs-rescue configuration template` 生成，
在初始化前审查修改上述资源字段，再通过守护进程的本机 `--setup-config ID=/absolute/private-config.json`
预置及受保护首次初始化选择使用。配置由核心校验，文件权限和磁盘白名单仍须符合
[救援工具的草稿说明](components/rescue.md#uninitialized-configuration-drafts)。这不是 Web 在线资源配置页。
已有池的系统目录及各元数据成员均持有配置锚；不得通过只改系统目录 `config.json` 来宣称完成安全调额，
也不得删除清单释放名额。现阶段耗尽后的在线调额、离线一致调额流程均未实现，应在部署评估中明确这一限制。
测试中的配置降低/恢复只验证预算拒绝不会丢失证据，不构成运维调额接口。

当前仅提供有界准入与安全拒绝，没有工作区证据生命周期退休机制。
每工作区保留的 `.full` 和 `.prepared` 代际文件总数还受 `max_entries` 限制，
包含零字节文件和尚未进入清单的残留代际；同一已存在代际的无新增文件重试不占新名额。
此检查复用暂存目录用量扫描，不读取文件内容，也不按每次清单变更扫描目录。
