# 源码命名迁移与来源架构

[命名规范](../NAMING.md) · [源码治理工具](../tools/rust-sources.md) · [单仓库结构](../monorepo.md)

## 状态与边界

本文描述命名迁移的约束及分阶段实现。首批六组件映射见[命名规范](../NAMING.md)，活动源码、内部引用及测试目录已协调改名。`manage.py refresh --rename-plan` 使用明确的前后清单生成不可变的改名记录；具体边界以实现和测试为准。第二批界面组件族也已迁移；其他候选组件族仍为计划。

源码整合已具有单 Git 仓库、根 Cargo workspace、根活动 Cargo.lock 和中央许可证/来源材料。下一步是使活动组件名及内部标识表达职责；逻辑整合不授权删除任何远端仓库。

## 三种身份分离

1. **活动身份**：当前目录、Cargo 包名/版本、Rust crate 标识、消费者及当前文件摘要。允许经过审阅的命名迁移。
2. **原始来源身份**：原始包名/版本、origin_directory、归档 URL/SHA-256、原始逐文件摘要、许可证及版权。不可因改名覆盖。
3. **互操作身份**：协议字段、文件格式、系统 ABI、绑定元数据和外部符号。默认不随内部命名变化；需要具体边界说明及兼容性测试。

安全扫描应继续使用真实上游身份匹配公告，而不是用新的内部包名逃过匹配。目录重命名不等于上游升级，也不能伪装成退役后重新导入。

## 现有门禁与迁移要求

现有 refresh 会比较实际源码目录与已登记目录；普通刷新不能把目录消失解释为已批准重命名。测试分离收据还固定了原始源码、输出路径、输出内容和可逆重建信息。直接改目录、修改冻结收据或重新接受所有摘要都会破坏这条证据链。

命名迁移应增加明确审阅的迁移层，至少验证：

- 迁移前活动包收据完全匹配；旧路径、新路径及身份映射唯一。
- 新路径位于允许的仓库目录，目标无覆盖冲突；拒绝路径逃逸、符号链接和特殊文件。
- 文件清单有精确的前后路径、内容摘要和必要的修改说明；新增、删除或文本改写必须明确登记。
- 同批迁移的活动测试 owner、测试路径和源码归属同步变更；历史来源键及旧收据原样保留，通过映射连接到当前实现。
- 迁移前后 origin_directory 与真实上游身份不变，许可证材料及原始收据摘要不变。
- 已退役/已替代历史不改写；若活动路径涉及替代链，新增映射应可把历史终点解析到当前实现，不能静默换掉历史键。
- 迁移记录可重复验证；普通 refresh 不得把未审阅的路径变化、测试缺失或来源丢失合法化。

内部文件改名使用可选 `file_moves` 清单：对完整迁移前后文件集合要求双射，未列出的文件按同一相对路径对应，拒绝未知源、目标覆盖及遗漏。它不能代替单独的新增/裁剪审阅。

目录移动和内部代码改写是不同维度。路径映射不足以批准任意字节变化，反之文本替换清单也不足以证明未丢失文件。已有不可变测试搬迁收据应继续能够核验历史基线，不能为了让新代码通过而把其固定摘要换成新值。

## 首批边界

首批为 bitflags、itertools、rand_core、sha2、shlex 及合并后的 base64 六个单版本组件；SHA-2 和 Base64 保留功能性包名，仅移除目录的发布版本。六项均有分离测试 owner，没有附着于当前目录的 superseded 记录。Base64 的旧实现已通过差异验证并按明确移除计划归档，合并不是单纯改名。

该批次同时检查 Cargo 包名、显式 lib 名称、依赖别名、feature 转发、Rust 引用、宏展开、活动 doctest 和测试路径；不改变算法、线格式、原始许可证或来源版本。完整前后清单及测试结果应由实施收据记录，不能仅依赖本文。

## 后续高耦合组件

### 界面及过程宏

web-interface 现重导出 dom-helpers、view-renderer，并使用 reactive-state。view-macros 的生成路径已改为 web_interface::view_renderer。库重导出、宏 token、消费者、调试 cfg、SharedValue 类型及活动文档测试联合修改；浏览器行为验收与 WASM 编译分别报告。

### 派生与运行时宏

错误派生实现存在硬编码的 ::thiserror 路径；序列化派生和异步入口宏也有辅助属性、默认 crate 路径和隐藏支持模块。按完整组件族迁移，并编译真实消费者与文档示例。数据字段、错误语义和协议表示保持不变。

### 原生密码与 WASM 绑定

ring 的构建脚本使用 Cargo 包名及版本构建原生符号前缀，并检查 links 值；预生成汇编与该前缀相关。内部包改名之前必须将活动包身份与固定 ABI 命名解耦，或执行经过完整验证的符号再生成。后者不是首批范围。

WASM 绑定同时包含 Rust 宏、共享 schema、生成 JS 和工具端解释器。内部品牌标识可以计划迁移，但导入/导出符号、绑定元数据及工具识别契约必须逐项识别，不能把全仓字符串替换当作兼容性证据。

## 多版本组件的处理

重复版本不只是命名问题。比如两代块缓冲实现分别使用 generic-array 与 hybrid-array，类型和 trait 关系不能靠改成同一个目录解决。语法解析、哈希表、熵获取及编码组件也需要按真实消费者核查。

先决定是否能够安全统一实现；无法统一时用实现特征或稳定职责区分，并保留每个来源映射。避免用当前临时消费者生造误导性名字，也避免以兼容层无限保留两个相同职责的实现。合并、上游升级、退役和命名迁移分别给出证据，不混为一次无边界刷新。

## 验证顺序与完成判据

1. 固定基线及已有未提交修改，先处理现有验证故障。
2. 审查命名映射和例外；验证新名无碰撞、无发布版本后缀。
3. 先测试迁移治理，再执行明确批准范围内的路径和代码变更。
4. 离线解析五个登记入口闭包，检查完整 manifest 特性边、路径依赖及根锁文件。
5. 运行治理工具单元测试、来源验证、受影响组件及真实消费者的单元/集成/文档测试。
6. 按范围执行 native/WASM 构建、原生 ABI 或密码回归、Web 新鲜度与发布检查；浏览器、Samba 和部署验收单独记录。
7. 生成当前来源文档，检查历史材料字节未变。逐项解释活动源码中的旧名残留，不删除法律归属以追求零匹配。

只有已验证的范围标为完成；候选名称、编译通过、真实运行验收及剩余迁移范围应明确区分。
