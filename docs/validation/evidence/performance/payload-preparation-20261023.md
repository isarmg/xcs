# 大候选准备阶段的完整哈希次数

本记录是开发模式、文件系统缓存已热的定向准备阶段实验，不是物理介质或端到端提交基准。优化仅作用于 `PayloadPreparation::verify` 的超过 32 个正文副本路径；128 个持有文件描述符的阈值不变。

## 改动与安全边界

旧路径先完整验证每个副本、立即丢弃其证明，然后调用 `VerifiedPayloadSet::validate` 再完整验证一遍。此次删除前一轮被丢弃的重复工作。保留的一轮仍验证完整正文、分块哈希、版本与校验清单，并保留 inode、链接数、大小、ctime 和元数据检查。准备前持有的磁盘目录与封印身份在验证前后均检查。

未删除决定阶段或恢复阶段校验。小候选仍保留逐副本证明，只增加最后的磁盘身份检查。本次没有解决 State 克隆、快照编码、历史回执增长或其他发布阶段重复校验，不宣称整个提交耗时降低 50%。

## 重现

在仓库根目录使用项目工具链：

```sh
cargo test --offline --locked -p storage-engine --lib verified_payloads::tests
cargo test --offline --locked -p storage-engine --lib benchmark_large_preparation_hash_passes -- --ignored --nocapture
```

手动基准创建 11 个 1 MiB 版本，每个 3 个副本，进行四轮交替先后顺序的比较。`reference_prepare` 保留旧重复哈希路径，并使用相同的当前副本校验器与磁盘检查，以隔离被删除的工作。计数器仅用于测试且为线程局部。`payload_bytes` 统计校验时读取的字节，不把分块与整文件哈希的输入重复相加。

计时包括元数据读取与验证，不包括夹具创建、编译和后续决定阶段校验。使用未优化测试 profile，计时只是观察值，不设为 CI 性能阈值。

## 确定性回归

- 恰好 32 个副本：优化前后均为 32 次副本完整验证，仍保留持有证明。
- 恰好 33 个副本：66 次降为 33 次，不保留逐副本证明。
- 11 个 1 MiB 版本 × 3 个副本：准备阶段读取量由 69,206,016 降为 34,603,008 字节，仅该阶段下降 50%。
- 最后一个副本损坏时，新旧路径均返回 `CHECKSUM_MISMATCH`。
- 哈希前替换磁盘封印，在读取正文前拒绝。
- 最后副本验证后以相同字节替换封印，被最后的持有身份检查拒绝。
- 既有用例继续覆盖原地篡改、校验文件 inode 替换、候选元数据变化、拓扑变化和失效的锁外准备。

## 实际记录（2026-10-23）

[原始输出](../../../../tools/perf-check/results/20261023-payload-preparation/warm-debug-run.txt)记录已编译测试程序的一次成功四轮实验。每轮字节数和验证次数均符合上述断言。参考路径耗时 170.5–252.9 ms，优化路径 87.7–123.9 ms；中位数分别为 209.6 ms 和 97.4 ms。

实验同时存在其他编译活动且缓存已热，这些时间不能视为稳定生产延迟保证。可重复断言是该准备阶段完整正文验证读取量减半。

修改后的定向证明测试通过 10 项，手动基准默认忽略后另行执行通过。更广的 `engine::publication::` 测试通过 13 项，另 1 项手动基准忽略，覆盖缓存预算回滚/重试及有界并行准备：

```sh
cargo test --offline --locked -p storage-engine --lib engine::publication::
```

本次不改变线上格式、恢复语义、阈值或权威 State schema。
